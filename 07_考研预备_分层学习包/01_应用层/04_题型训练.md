## 5. DNS 题型

### 5.1 DNS 的作用

```text
DNS 用于将人容易记忆的域名解析为网络通信所需的 IP 地址。
```

注意区分：

```text
DNS：域名 -> IP
ARP：IP -> MAC
```

### 5.2 递归查询和迭代查询

递归查询：

```text
客户端把查询任务交给 DNS 服务器，由 DNS 服务器继续查询并最终返回完整结果。
```

迭代查询：

```text
DNS 服务器不一定直接返回最终答案，而是告诉查询者下一步应该问哪个 DNS 服务器。
```

### 5.3 DNS 简答模板

```text
DNS 是域名系统，用于将域名解析为 IP 地址。
主机通常先查询本地域名服务器；如果本地域名服务器没有缓存结果，
则继续向根域名服务器、顶级域名服务器、权威域名服务器查询，
最终获得目标主机 IP 地址并返回给客户端。
```

### 5.4 DNS 常见考法

| 考法 | 答题关键词 |
|---|---|
| DNS 作用 | 域名解析为 IP |
| DNS 用 TCP 还是 UDP | UDP 为主，TCP 可用 |
| 递归 vs 迭代 | 是否由被查询服务器负责查到底 |
| DNS 与 ARP 区别 | DNS 域名到 IP，ARP IP 到 MAC |

## 6. HTTP/HTTPS 题型

### 6.1 HTTP 基础

HTTP 是超文本传输协议，采用请求-响应模式。

WWW 由浏览器、Web 服务器、HTML/超链接和 URL 共同组成。URL 用来定位资源，基本格式为：

```text
协议://主机:端口/路径
```

判断 URL 时要能区分协议、主机、可省略的默认端口和资源路径。

常见特点：

```text
默认端口 80
无状态
请求-响应模式
HTTP/1.x、HTTP/2 基于 TCP；HTTP/3 基于 QUIC/UDP
HTTP 本身不提供安全机制；明文 HTTP 不加密，HTTPS 使用 TLS
```

### 6.2 为什么 HTTP 无状态

```text
HTTP 协议本身不会自动记住前后请求之间的用户状态。
每个请求在协议层面相对独立。
如果应用需要保持登录状态或用户身份，通常借助 Cookie、Session、Token 等机制。
```

### 6.3 HTTPS

HTTPS 可以理解为：

```text
HTTPS = HTTP + TLS/SSL
```

提供：

```text
加密
身份认证
完整性保护
```

### 6.4 HTTP 和 HTTPS 区别模板

```text
HTTP 是明文传输协议，默认端口 80，数据在传输过程中容易被窃听或篡改。
HTTPS 在 HTTP 基础上加入 TLS/SSL，默认端口 443，
提供加密传输、服务器身份认证和数据完整性保护，因此安全性更高。
```

### 6.5 常见陷阱

| 题干 | 判断 |
|---|---|
| HTTPS 不需要 HTTP | 错，HTTPS 是 HTTP 加安全层 |
| HTTP 是有状态协议 | 错，HTTP 本身无状态 |
| Cookie 可帮助 HTTP 维持状态 | 对 |
| HTTPS 默认端口 80 | 错，HTTPS 默认 443 |

### 6.6 HTTP 状态码（选择/判断常出）

| 状态码 | 含义 | 说明 |
|:-----:|------|------|
| **200** | OK | 请求成功 |
| **301** | 永久重定向 | 资源换了新地址，以后用新地址 |
| **302** | 临时重定向 | 资源临时在别处，下次还用原地址 |
| **304** | Not Modified | **协商缓存**：客户端发条件请求（If-Modified-Since/If-None-Match），服务器确认资源未修改 → 304，客户端用缓存（未过期的强缓存通常根本不发请求） |
| **400** | Bad Request | 请求语法错误，服务器看不懂 |
| **403** | Forbidden | 服务器拒绝执行 |
| **404** | Not Found | 资源不存在 |
| **500** | Internal Server Error | 服务器内部出错 |
| **502** | Bad Gateway | 代理/网关收到上游无效响应 |
| **503** | Service Unavailable | 服务器暂时无法处理（过载/维护） |

> **速记口诀：** 2xx成功 3xx重定向 4xx客户端错 5xx服务端错

### 6.7 GET vs POST 区别（简答常考）

| 对比维度 | GET | POST |
|---------|-----|------|
| 参数位置 | 通常 URL 中（?key=value） | 通常请求体（Body）中 |
| 可见性 | 明文可见，会留在浏览器历史/服务器日志 | 请求体在开发者工具中也可见，未用 HTTPS 时同样可被窃听 |
| 长度限制 | 受 URL 长度限制（浏览器/服务器决定） | 受客户端和服务器限制，无协议硬性上限 |
| 安全性 | 低（参数暴露在 URL） | **并不天然更安全**——安全性主要取决于 HTTPS，与方法名无关 |
| 幂等性 | **方法语义上幂等**（重复执行对服务器效果与一次相同） | **方法不保证幂等**（多次提交可能产生多个资源/多次副作用） |
| 可缓存 | ✅ 通常可缓存 | 满足缓存条件时 HTTP 也允许缓存 POST 响应 |
| 可书签 | ✅ 可收藏为书签 | ❌ 不可以 |
| 数据类型 | 经 URL 编码后可携带非 ASCII | 任意类型（二进制也可） |

> **简答题模板：**
> ```text
> GET 和 POST 是 HTTP 最常用的两种请求方法。
> GET 参数放在 URL 中，适合获取资源，通常可缓存、可收藏书签，且语义上幂等。
> POST 参数放在请求体中，适合提交数据（表单、上传），语义上不幂等。
> 注意：POST 并不天然更安全——两者在未用 HTTPS 时都明文传输，
> 安全性的关键在 TLS 加密，而不是方法名。
> ```

### 6.8 HTTP 版本进化 + 持久连接

```text
HTTP/0.9 (1991)：只有 GET，纯文本
HTTP/1.0 (1996)：增加 POST、状态码、Header，每个请求一个TCP连接
                   ↓ 问题：一个页面有10张图片就要建10次TCP连接
HTTP/1.1 (1997)：默认持久连接（Keep-Alive），支持流水线（不默认启用）
                   ↓ 优化：同一TCP传多个请求，但请求级队头阻塞仍存在
HTTP/2   (2015)：多路复用、头部压缩、服务器推送
                   ↓ 解决请求级队头阻塞；但多个流共用一条TCP，
                   ↓ 发生丢包时仍有 TCP 层队头阻塞 ← HTTP/3 改用 QUIC 的原因
HTTP/3   (2022)：基于 QUIC（UDP），消除不同 QUIC 流之间由 TCP 统一字节流造成的队头阻塞（同一 QUIC 流内部丢包仍需等待）
```

**核心对比（考试重点）：**

| | 非持久连接（HTTP/1.0） | 持久连接（HTTP/1.1 默认） |
|--|----------------------|------------------------|
| 行为 | 每个对象建立一次TCP | 同一TCP传多个对象 |
| 效率 | 低（多次握手+慢启动） | 高（复用连接） |
| 默认 | HTTP/1.0 默认非持久 | HTTP/1.1 默认持久 |

> **考试答题模板：**
> ```text
> 持久连接（Keep-Alive）让多个 HTTP 请求复用同一个 TCP 连接，
> 减少了重复建立连接带来的三次握手和慢启动开销，
> 从而降低了访问延迟，提高了传输效率。
> HTTP/1.1 默认使用持久连接，而 HTTP/1.0 默认使用非持久连接。
> ```

**速记口诀：**

```text
HTTP 版本进化：0.9 → 1.0（每图一连接）→ 1.1（持久连）→ 2（多路复用）→ 3（QUIC）
每个版本解决什么问题：慢 → TCP次数太多 → 队头阻塞 → TCP也队头阻塞
```

## 7. FTP 题型

### 7.1 FTP 的双连接

FTP 使用两个连接：

```text
控制连接：传输命令和响应，常用 TCP 21。
数据连接：传输文件数据，按需建立。
```

### 7.2 为什么使用双连接

**真实原因：带外（Out-of-band）控制 —— 控制与数据分离，互不阻塞。**

```text
如果命令与数据共用一条 TCP 连接，FTP 就必须在同一个字节流中区分
命令和数据（需要定义分帧/多路复用机制），协议实现复杂度高；
而且大文件传输期间，命令的及时响应难以保证。

双连接解决这个问题：
  控制连接（21）→ 传命令，随时可用
  数据连接 → 传文件，用完即关；端点按主动/被动模式确定
  
  传输期间仍可通过独立控制连接发送 ABOR、STAT 等传输控制命令；
  普通命令是否立即执行取决于 FTP 状态和服务器实现。
```

**类比理解：**
```text
单连接 ≈ 只有一条马路，货车（数据）和小轿车（命令）一起堵着
双连接 ≈ 专门给货车修一条路，小轿车走另一条路，互不干扰
```

**考试答题模板（直接背）：**
```text
FTP 采用双连接设计，核心原因是为了实现带外控制。
控制连接（TCP 21）专门传输命令，在整个会话期间保持打开；
数据连接按需建立，传完即关：主动模式由服务器以源端口 20
连接客户端声明的临时端口；被动模式由客户端连接服务器临时端口。
独立控制连接使传输期间仍可发送适用的控制命令，避免命令与文件数据混在同一字节流。
```

### 7.3 主动/被动模式基线理解

主动模式：

```text
客户端告诉服务器自己的数据端口，服务器主动连接客户端的数据端口。
```

被动模式：

```text
服务器开放一个数据端口，客户端主动连接服务器的数据端口。
```

考试不一定深考，但看到 `PORT/PASV` 要知道和 FTP 数据连接建立方式有关。

## 8. 电子邮件协议题型

### 8.1 三个协议

| 协议 | 作用 | 关键词 |
|---|---|---|
| SMTP | 发送邮件 | 客户端到邮件服务器、邮件服务器之间转发 |
| POP3 | 接收邮件 | 下载到本地，较简单 |
| IMAP | 接收/管理邮件 | 在线管理，多设备同步更方便 |

### 8.2 必背句

```text
SMTP 负责发邮件。
POP3 和 IMAP 负责收邮件。
IMAP 更适合在服务器上在线管理邮件，多设备同步体验更好。
```

### 8.3 MIME 和 base64

为什么需要 MIME：

```text
传统邮件主要支持简单文本，MIME 扩展了邮件格式，使邮件可以携带非 ASCII 文本、图片、音频、附件等多种内容。
```

base64：

```text
把二进制数据转换成文本形式，便于在只适合传输文本的系统中传输。
3 字节通常编码成 4 个字符，体积约增加 33%。
```

邮件基本格式：首部 + 空行 + 主体。常见首部包括 `From`、`To`、`Subject`；MIME 通过 `Content-Type`、`Content-Transfer-Encoding` 等字段描述附件和非 ASCII 内容。

基于 Web 的电子邮件中，浏览器与邮件系统之间使用 HTTP/HTTPS；邮件服务器之间仍使用 SMTP。IMAP 是独立的邮件访问协议，不等同于 Web 邮件。

### 8.4 常见陷阱

| 题干 | 判断 |
|---|---|
| SMTP 主要用于接收邮件 | 错 |
| POP3 和 IMAP 都与接收邮件有关 | 对 |
| MIME 用于扩展邮件可承载内容类型 | 对 |
| base64 编码会压缩数据 | 错，通常会膨胀 |

## 9. Cookie、缓存、CDN 题型

### 9.1 Cookie

```text
Cookie 是服务器通过浏览器保存在客户端的小段信息，
常用于用户识别、登录状态维持、个性化设置等。
```

### 9.2 Web 缓存

```text
Web 缓存保存用户访问过的资源副本。
再次访问相同资源时，可直接从缓存获取，减少访问时延，降低服务器和网络负载。
```

### 9.3 CDN

```text
CDN 是内容分发网络，通过在不同地理位置部署缓存节点，
让用户从距离更近的节点获取资源，提高访问速度并减轻源站压力。
```

### 9.4 对比表

| 机制 | 解决什么问题 |
|---|---|
| Cookie | HTTP 无状态下的状态保持 |
| Web 缓存 | 重复资源访问慢、服务器压力大 |
| CDN | 用户离源服务器远、访问延迟高 |

### 9.5 提高访问速度/降低延迟（高频题型）

**考题不会直接问"缓存是什么"，而是问：**

| 考题实际问法（伪装版） | 真实考点 |
|----------------------|---------|
| "视频网站如何让全国用户都流畅观看？" | CDN 就近分发 |
| "再次访问同一个网页为什么比第一次快？" | 稳定原因是缓存命中；若原连接仍有效，持久连接还能省去建连开销 |
| "某网站用户量暴增，服务器压力大，怎么优化？" | Web 缓存 / CDN |
| "如何减少用户访问资源的响应时间？" | 缓存 + CDN + 持久连接 |
| "多个用户访问同样资源，怎样避免重复请求源服务器？" | Web 缓存 / CDN |

**应答核心逻辑（三步递进）：**

```text
第一步：Web 缓存（浏览器/代理缓存）
  "把用户访问过的资源存在本地或代理服务器上，
  下次访问相同资源直接取缓存，不去源服务器请求。
  减少重复请求 → 降低时延 + 减轻源站压力。"

第二步：CDN（内容分发网络）
  "如果用户和源服务器距离很远（比如新疆访问北京的服务器），
  CDN 在全国各地部署缓存节点，
  让用户从最近的节点获取资源。
  缩短物理距离 → 降低传播时延。"

第三步：持久连接（HTTP/1.1 Keep-Alive）
  "在同一个 TCP 连接上传输多个 HTTP 请求响应，
  避免重复建立连接的开销。
  减少三次握手 → 降低连接建立时延。"
```

**考试综合答题模板：**

```text
提高网络访问速度、降低延迟的手段主要包括：

1. Web 缓存：缓存用户已访问的资源副本，再次访问时直接命中缓存，
   减少重复请求和网络传输。

2. CDN：将内容分发到离用户更近的边缘节点，用户就近获取资源，
   缩短传播距离，降低响应时间。同时分担源服务器压力。

3. 持久连接（HTTP Keep-Alive）：让多个 HTTP 请求复用同一个 TCP 连接，
   减少三次握手和慢启动带来的额外时延。

实际中通常三者结合使用：CDN 做全局加速，Web 缓存做局部加速，
持久连接优化单次会话效率。
```

这类题经常是综合题，可以按层次写。


## 12. 简答模板库

### DNS 的作用是什么

```text
DNS 用于将人容易记忆的域名解析为网络通信所需的 IP 地址。
客户端通常先向本地域名服务器发起查询；
若本地域名服务器没有缓存结果，则继续通过递归或迭代方式查询根域名服务器、顶级域名服务器和权威域名服务器，
最终获得目标主机 IP 地址。
```

### HTTP 和 HTTPS 区别

```text
HTTP 是明文传输协议，默认端口 80。
HTTPS 是在 HTTP 基础上加入 TLS/SSL，提供加密、身份认证和完整性保护，默认端口 443。
因此 HTTPS 安全性更高，但建立连接和加密处理开销也更大。
```

### FTP 为什么使用双连接

```text
FTP 使用控制连接传输命令和响应，使用数据连接传输文件内容。
控制连接通常使用 TCP 21 端口并在会话期间保持；
数据连接按需建立，用于实际文件传输。
这种设计使控制信息和文件数据相互独立。
```

### HTTP 为什么无状态

```text
HTTP 协议本身不会自动保存客户端前后请求的状态，每个请求在协议层面相对独立。
为了实现登录保持、购物车等功能，Web 应用通常借助 Cookie、Session 或 Token 维护状态。
```

### Cookie、缓存、CDN 的作用

```text
Cookie 用于在客户端保存状态信息，帮助 HTTP 应用识别用户。
Web 缓存用于保存资源副本，减少重复请求和访问时延。
CDN 通过分布式节点就近提供内容，提高访问速度并减轻源站压力。
```

### P2P 和 C/S 架构的区别

```text
C/S 架构中，客户端向中央服务器请求资源，服务器压力随用户数增加而增大，可扩展性差。
P2P 架构中，每个节点既是客户端也是服务器，下载的同时也上传，
因此节点越多、系统总资源越丰富，具有自扩展能力。
P2P 适合文件分发场景（如 BitTorrent），但安全性和可控性不如 C/S。

P2P 的三种实现方式：
- 集中式：有中心索引服务器（Napster）
- 完全分布式：无中心、全靠邻居转发（Gnutella）
- 混合式：有 Tracker 但传输是 P2P（BitTorrent）
```

### 15.1 考点一：网络应用模型（C/S vs P2P）

**2019 真题（单选）**：下列关于网络应用模型的叙述中，错误的是：

| 选项 | 判断 |
|------|------|
| A. P2P 模型中，结点之间是对等关系 | 正确 |
| B. C/S 模型中，客户与客户之间可以直接通信 | **错误（选这个）** |
| C. C/S 模型中，主动发起通信的是客户，被动通信的是服务器 | 正确 |
| D. 向多用户分发一个文件时，P2P 模型通常比 C/S 模型所需时间短 | 正确 |

> 关键区分：在该 C/S 应用模型定义的通信中，客户进程之间**不直接通信**，由服务器进程提供服务；P2P 应用中的对等进程可直接通信。

### 15.2 考点二：DNS 系统

**2018 真题（第 33 题，单选）**：下列 TCP/IP 应用层协议中，可以使用传输层无连接服务的是？

| 选项 | 协议 |
|---|---|
| A | FTP |
| B | DNS |
| C | SMTP |
| D | HTTP |

> 答案：**B，DNS**。常规 DNS 查询可使用 UDP 提供的无连接服务；FTP、SMTP 和传统 HTTP 均基于 TCP。

**2010 真题（单选）**：如果本地域名服务器无缓存，采用**递归方法**解析另一网络主机域名时，用户主机、本地域名服务器发送的域名请求消息数分别为？

| 选项 | 用户主机、本地域名服务器 |
|---|---|
| A | 一条、一条 |
| B | 一条、多条 |
| C | 多条、一条 |
| D | 多条、多条 |

> 答案：**B，一条、多条**。用户主机只向本地 DNS 发起一次递归查询；本地 DNS 无缓存，需要继续向多个域名服务器发出查询。
> 对比：迭代查询是执行解析的服务器逐级指路、多次查询——408 典型流程是主机只问本地 DNS 一次（递归），由本地 DNS 对根/TLD/权威逐级迭代；「谁发多次」取决于谁是迭代查询的执行者。

**2016 真题（单选）**：假设所有域名服务器均采用**迭代查询**，当主机访问 www.abc.xyz.com 时，域名服务器（最左侧的本地域名服务器）在完成解析过程中**可能发出**的 DNS 查询的**最少和最多**次数分别是？

| 选项 | 最少、最多 |
|---|---|
| A | 0、3 |
| B | 1、3 |
| C | 0、4 |
| D | 1、4 |

> 答案：**C，0 和 4**。
> - 最少 0 次：本地域名服务器缓存命中的话根本不用发查询
> - 最多 4 次：本地 DNS → 根 → TLD(.com) → 二级(.xyz) → 权威(.abc)，共 4 次迭代
> - 记忆法：递归 = 别人替你查（你只问 1 次）；迭代 = 别人告诉你去问谁（每次都要自己问）

**2020 真题（第 40 题，单选+计算）**：本地域名服务器只提供**递归服务**，其他域名服务器只提供**迭代服务**；局域网内主机访问 Internet 上各服务器的往返时间（RTT）均为 **10ms**，忽略其他各种时延。主机通过超链接 http://www.abc.com/index.html 访问纯文本 Web 页面，从点击超链接开始到浏览器接收到 index.html 页面为止，所需的最短与最长时间分别是？

| 选项 | 最短、最长 |
|---|---|
| A | 10ms、40ms |
| B | 10ms、50ms |
| C | 20ms、40ms |
| D | 20ms、50ms |

> 答案：**20ms 与 50ms（D）**。
> - 最短：本地域名服务器缓存命中；局域网内查询时延按题意忽略，只需 TCP 建连 1 RTT + HTTP 请求/响应 1 RTT，共 **20ms**
> - 最长：本地 DNS 分别查询根、`.com` 顶级域和 `abc.com` 权威服务器，共 3 个 Internet RTT，即 30ms；再加 TCP 和 HTTP 的 20ms，共 **50ms**
> - 易错点：H 与本地 DNS 同在局域网，题目只给“访问 Internet 上各服务器”的 RTT，不能再给 H→本地 DNS 自造 1 个 10ms RTT
> - 综合题套路：总时延 = DNS 解析时延 + TCP 建立时延 + HTTP 传输时延

**2021 真题（第 47 题，综合大题，跨层）**：H1、H2、本地域名服务器和路由器 R 通过以太网交换机 S 互联。`t0` 时 H1 的 ARP 表和 DNS 缓存均为空；H1 通过域名 `www.abc.com` 访问 Internet 上的 Web 服务器，`t1` 时 S 第一次收到封装 HTTP 请求报文的以太网帧。问：
1. H1 除 HTTP 外还运行了哪个应用层协议？该应用层报文从应用层到数据链路层依次通过哪些协议封装？
2. 若 S 的交换表结构为 `<MAC 地址, 端口>`，`t1` 时交换表中有哪些表项？
3. 从 `t0` 到 `t1`，H2 至少收到几个与本次 Web 访问有关的帧？它们是什么帧，目的 MAC 地址是什么？

> 参考答案（据原题 PDF 第 4 页拓扑）：
> 1. 除 HTTP 外还运行 **DNS**；DNS 报文依次封装在 **UDP -> IP -> 以太网** 中。
> 2. S 通过源地址自学习得到三项：`<00-11-22-33-44-cc, 4>`（H1）、`<00-11-22-33-44-bb, 1>`（本地域名服务器）、`<00-11-22-33-44-aa, 2>`（路由器 R）。H2 在此期间未发送帧，因此没有 H2 的表项。
> 3. 至少 **2 个帧**，都是 H1 发出的 **ARP 请求广播帧**：一次查询本地域名服务器的 MAC，一次查询默认网关 R 的 MAC；两帧的目的 MAC 地址均为 `FF-FF-FF-FF-FF-FF`。交换机把广播帧泛洪到 H2 所在端口 3。
> 考点：DNS 的逐层封装、ARP 广播、交换机源地址自学习和未知/广播帧转发。

### 15.3 考点三：FTP

**2009 真题（单选）**：FTP 客户和服务器之间传输 FTP 命令时，使用的连接是？

> 答案：**建立在 TCP 之上的控制连接**（传输命令走控制连接，客户端主动连服务器 21；数据连接也基于 TCP，但**端口不是固定 20**——主动模式下 20 只是服务器数据连接的**源端口**，被动模式用服务器临时端口）。

**2017 真题（单选）**：下列关于 FTP 协议的叙述中，错误的是：

| 选项 | 判断 |
|------|------|
| A. 数据连接在每次数据传送完毕后即关闭 | 正确 |
| B. 控制连接在整个会话期间保持打开状态 | 正确 |
| C. 服务器与客户端的 TCP 20 端口建立数据连接 | **错误（选这个）**——20 是服务器数据连接的**源端口**，目标是客户端声明的临时数据端口，客户端没有固定 20 端口 |
| D. 客户端与服务器的 TCP 21 端口建立控制连接 | 正确——控制连接正是客户端主动连服务器 21 |

> 方向辨析：控制连接 = **客户端主动连服务器 21**（标准流程）；
> 主动模式下数据连接 = 服务器以**源端口 20** 主动连客户端通过 PORT 命令声明的数据端口（客户端数据端口是临时端口，不固定为 20）。
> 记忆：21 是服务器监听控制连接；20 是服务器数据连接的源端口。

**2023 真题（综合大题 9 分，第 1 问节选：FTP 连接性质）**：主机 H 登录 FTP 服务器后上传文件，传输中未发生差错和乱序。原题后续 TCP 数值小问未收录；本节只问：
1. FTP 的控制连接是持久的还是非持久的？
2. FTP 的数据连接是持久的还是非持久的？
3. H 登录 FTP 服务器时建立的 TCP 连接是控制连接还是数据连接？

> 参考答案：控制连接**持久**（整个会话保持）；数据连接**非持久**（每次传输新建，传完关闭）；登录时建立的是**控制连接**。
> （原题另有 TCP 拥塞控制的数值小问，依赖初始序号、MSS、RTT 等条件；本资料按考点拆分，数值问见 02_运输层 真题专章）

### 15.4 考点四：电子邮件

**2018 真题（单选）**：无须转换即可由 SMTP 协议直接传输的内容是？

**2015 真题（单选）**：通过 POP3 协议接收邮件时，使用的传输层服务类型是？

| 选项 | 服务类型 |

| A | 无连接不可靠的数据传输服务 |

| C | 有连接不可靠的数据传输服务 |
| D | 有连接可靠的数据传输服务 |

> 答案：**D，有连接可靠的数据传输服务**（POP3 基于 TCP）。

**2025 真题（单选）**：下列关于 POP3 协议的叙述中，正确的是？

```text
I.   支持用户代理从邮件服务器读取邮件
II.  支持用户代理向邮件服务器发送邮件
III. 支持邮件服务器之间发送和接收邮件
```

| C | II、III |
| D | I、II、III |

> 答案：**B（I、IV）**。II 属于 SMTP 的用户提交，III 属于 SMTP 的服务器间转发。

### 15.5 考点五：HTTP（最高频）

**2014 真题（单选）**：使用浏览器访问某大学 Web 网站主页时，**不可能**使用到的协议是？

| 选项 | 协议 |
|---|---|
| A | PPP |
| B | ARP |
| C | UDP |
| D | SMTP |

> 答案：**D，SMTP**。PPP 可能用于接入链路，ARP 可能用于局域网地址解析，UDP 可能承载 DNS；SMTP 与浏览网页无关。

**2015 真题（单选，报文分析）**：某浏览器发出的 HTTP 请求报文如下：

```
GET /index.html HTTP/1.1
Host: www.test.edu.cn
Connection: Close
Cookie: 12345
```

| 选项 | 叙述 |
|---|---|
| A | 该浏览器请求浏览 index.html |
| B | index.html 存放在 www.test.edu.cn 上 |
| C | 该浏览器请求使用持续连接 |
| D | 该浏览器曾经浏览过 www.test.edu.cn |

> 答案：**C**。`Connection: Close` 明确要求响应后关闭连接，覆盖 HTTP/1.1 默认持久连接；A 由请求行判断，B 由 Host 首部判断，D 可由 Cookie 首部判断。

**2024 真题（单选，RTT 计算）**：若浏览器**不支持并行 TCP 连接**，使用**非持久**的 HTTP/1.0 协议请求浏览一个 Web 页面，页面中引用**同一网站上 7 个小图像文件**，从浏览器为传输 Web 页面建立 TCP 连接开始到接收完所有内容为止，所需往返时间 RTT 数量至少是？

| 选项 | RTT 数 |
|---|---:|
| A | 4 |
| B | 9 |
| C | 14 |
| D | 16 |

> 答案：**16 个 RTT**。
> 思路：不支持并行 TCP 连接 = 串行建立连接。
> 每个对象：建立 TCP 连接（1 RTT）+ HTTP 请求响应（1 RTT）= 2 RTT。
> 页面本身 1 个对象 + 同一网站 7 个小图像 = 8 个对象。
> 答案 16 = 8 对象 × 2 RTT（本题关键是"非持久连接每对象一次 TCP"，考的是连接建立开销的概念）。

**2011 真题（综合大题 9 分）**：某主机的 MAC 地址为 00-15-C5-C1-5E-28，IP 地址为 10.2.128.100（私有地址），图给出该主机进行 Web 请求的一个以太网数据帧前 80B 的十六进制及 ASCII 码内容。假设 HTTP/1.1 以持久、非流水线方式工作，一个请求-响应的时延为 RTT，HTML 页面引用了 5 个 JPEG 小图像，则从发出 Web 请求开始到浏览器收到全部内容为止需要多少个 RTT？

> 答案：**6 个 RTT**。
> 思路：持久非流水线：HTML 页面 1 RTT，然后 5 个图像**串行**请求（每个等响应）5 RTT，共 6 RTT。
> 对比：如果是流水线方式，页面 1 RTT + 5 图像 1 RTT = 2 RTT（管道化连续发送）。
> **RTT 计算三模式对比**（⚠️ 统一口径：N = 全部对象数含基础页面，如 HTML+5 图 = 6 个对象）：
> 计时起点必须先确认——题目说「从建立 TCP 连接开始」用左列；说「连接已建立/发出 Web 请求」用右列：
>
> | 模式 | 从首次建连计时 | 从连接已建立计时 |
> |------|:---:|:---:|
> | 非持久（每对象单独建连） | 2N | 2N-1（首个连接已建好，只省首对象的建连） |
> | 持久非流水线（逐对象请求） | 1 + N | N |
> | 持久流水线（至少有 1 个嵌入对象） | 3（建连 + 页面 + 同服务器嵌入对象一批） | 2（页面 + 同服务器嵌入对象一批） |
>
> 验证：2024 从建连非持久 2×8=16 ✓；2011 已建立持久非流水线 N=6 ✓。
> 注意：`N=1` 时没有嵌入对象，持久连接从建连/已建连计时分别为 2 RTT/1 RTT；跨服务器资源通常不能直接复用原连接。
> HTTP/2 的多路复用效果受连接复用、对象所在域和拥塞窗口影响，不作为固定 RTT 公式。
> 上表忽略 TCP 拥塞窗口限制；若题目给出 MSS、文件大小或慢开始条件，必须另画 TCP 发送轮次，不能直接套 3 RTT。
> **先确认计时起点再套公式，两列公式不可混用。**

**2022 真题（第 40 题，单选+计算）**：主机 H 通过 HTTP/1.1 请求浏览服务器 S 上的 Web 页 `news408.html`，该页面引用了同目录下的 **1 幅图像**；页面文件大小为 1 MSS，图像文件大小为 3 MSS。RTT=10ms，忽略 HTTP 响应首部开销和 TCP 段传输时延。H 已完成域名解析，从请求建立 TCP 连接到收到全部内容至少需要多久？

| 选项 | 时间 |
|---|---:|
| A | 30ms |
| B | 40ms |
| C | 50ms |
| D | 60ms |

> 答案：**40ms（B）**。
> 按 408 传统慢开始口径，TCP 初始拥塞窗口为 1 MSS：
> 1. 第 1 个 RTT：建立 TCP 连接，第三次握手可捎带 HTTP 请求
> 2. 第 2 个 RTT：服务器发送 1 MSS 的 HTML；确认后拥塞窗口增至 2 MSS
> 3. 第 3 个 RTT：服务器发送图像的前 2 MSS；确认后拥塞窗口增至 4 MSS
> 4. 第 4 个 RTT：服务器发送图像剩余 1 MSS
>
> 共 4 RTT = **40ms**。本题考的是 TCP 慢开始发送轮次，不是“多个图像能否流水线并发”。
